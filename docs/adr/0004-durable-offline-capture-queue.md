# ADR-0004: Durable offline capture queue and idempotency

- Status: Accepted
- Date: 2026-08-28

## Context

Ratatoskr Mobile must accept explicit URL, text-note, and app-owned staged-file references while
offline and retain them across process death. A crash can occur after Platform accepts a request
but before the client commits the response, so transport is necessarily at least once. The local
queue must preserve one stable effect identity, source ordering, retry timing, owner scope, and a
conservative Platform operation projection without moving share lifecycle or file authority into
shared code.

Ratatoskr is in development. The repository therefore keeps one current schema and forbids schema
migration files or compatibility readers.

## Options considered

1. Room 3.0.1 KMP with KSP and bundled SQLite.
2. SQLDelight with a second schema tool.
3. Separate native Android and iOS databases.
4. DataStore or preferences as the queue.

Room matches the accepted version catalog, supports the required transactional and indexed
invariants on both targets, and avoids duplicating the state machine. SQLDelight is viable but
would introduce a second persistence stack. Native databases duplicate correctness rules.
Preferences do not provide suitable transactions, uniqueness, or ordered claims.

## Decision

The shared module owns immutable capture models, `CaptureQueue`, retry and projection rules, and a
Room 3.0.1 KMP database generated by KSP. The database has one `capture_queue` aggregate table with
database-enforced uniqueness for the idempotency key and `(owner, source lane, source sequence)`.
No migrations exist; a schema change edits this one current schema and development/test stores are
recreated.

Each record contains one bounded URL, text note, or opaque staged-file reference plus owner, source,
creation time, stable local ID, deterministic request fingerprint, stable idempotency key, source
sequence, delivery state, retry metadata, lease data, safe failure class, operation binding, and a
minimized operation projection. Payloads and fingerprints are never diagnostic labels or log data.

Enqueue is atomic. Reusing an idempotency key with the same fingerprint converges on the existing
record; using it with different content fails closed. A network retry always reuses the persisted
key. Binding the same Platform operation twice is a no-op. If one key resolves to two operation IDs,
the record enters resolution conflict, preserves both IDs, and leaves automatic processing.

Queue order is FIFO within each owner-scoped source lane. Only its oldest unfinished record may be
claimed. Eligible lane heads are selected deterministically by next-eligible time, creation time,
then local ID. Every in-flight attempt receives a finite lease and opaque claim token. An expired
lease can be reclaimed after restart with the original idempotency key; a stale claim token cannot
mutate the newer attempt.

Retryable connectivity, server, and rate-limit failures use capped exponential backoff with equal jitter.
The first ceiling is 30 seconds, the local ceiling is six hours, and a later server hint is
bounded to 24 hours. Automatic attempts stop after 12 by default. Authentication pauses the lane;
validation, policy, size, and unrecoverable local-file failures are permanent.

Generated Platform `OperationSnapshot` values are reduced to a minimized projection. Older or
duplicate snapshots do not regress state, terminal state never regresses, and equal-time conflicts
fail closed.

## Native lifecycle and protection

Android and iOS pass explicit private database locations into the shared store. Android uses the
application-private database directory, and the application manifest keeps
`android:allowBackup="false"`. iOS applies
`NSFileProtectionCompleteUntilFirstUserAuthentication` to the SQLite database and existing WAL/SHM
sidecars after transactions. The iOS Simulator proves that the protection seam is invoked, but it
does not expose the protection attribute through `attributesOfItemAtPath`; attribute verification
on physical hardware remains a device-only release check.

Share Target, Share Extension/App Group coordination, staged-file ownership, WorkManager,
background URLSession, and network submission remain native or later orchestration work. They
consume `CaptureQueue`; they do not own its business truth.

## Security and privacy consequences

- The queue contains user URLs/text and must never be logged, placed in analytics, or backed up by
  Android.
- Staged paths are opaque app-owned identifiers; this item stores no external URI or
  security-scoped capability.
- Owner origin and account are explicit on every record and every claim.
- Capacity failures never evict unfinished user content.
- Secrets remain in Keystore/Keychain and are not columns in the Room database.
- OS file protection is the current local-at-rest boundary. Stronger database encryption requires
  a separate measured threat decision rather than an unreviewed dependency.

## Compatibility and schema impact

This is the first and only local queue schema. There is no production-data migration, fallback
reader, version negotiation, or parallel schema. The change consumes the pinned Platform operation
contract and adds no public API field or endpoint.

## Validation

- Common tests cover model bounds, exact serialization, idempotent enqueue, owner isolation,
  per-source FIFO, leases and stale tokens, equal-jitter backoff, server hints, exhaustion,
  resolution conflict, and monotonic operation projection.
- Android instrumentation and iOS Simulator tests create the current Room schema from an empty
  file, close it, reopen it, and compare payload, local ID, source sequence, and idempotency key.
- Android instrumentation uses the application-private, backup-disabled configuration.
- iOS Simulator tests verify the native file-protection seam is applied; physical-device attribute
  inspection is intentionally not claimed.

## Follow-up

Plan items 4 and 5 add native share intake and submission scheduling. Plan item 8 defines staged
file retention, cleanup, and stronger device lifecycle evidence. None of those items may bypass the
durable queue or replace its idempotency key during retry.
