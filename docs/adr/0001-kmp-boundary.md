# ADR-0001: Kotlin Multiplatform ownership boundary

Status: Accepted

Date: 2026-08-28

## Context

Ratatoskr Mobile needs one product experience on Android and iOS while its share surfaces, background execution, secure storage, and file grants obey different operating-system contracts. Sharing only leaf models would duplicate the presentation and state model; sharing platform lifecycle behind a uniform facade would conceal failure modes that determine whether a capture is durable and authorized.

The selected product stack uses Compose Multiplatform inside thin native application shells. This decision is the explicit ADR required by the repository rule that shared UI is not introduced by convention alone.

## Options considered

1. Fully native Android Compose and SwiftUI presentation. This keeps each UI conventional but duplicates navigation, UDF state, and presentation behavior.
2. Share every layer, including share intake and lifecycle. This maximizes code sharing but erases Android and iOS authority, lifetime, and error differences.
3. Share product presentation and business rules, retain native lifecycle and authority adapters. This has an interop cost but gives one product state model without treating unlike operating-system contracts as identical.

## Decision

Choose option 3.

### Shared KMP ownership

KMP owns behavior that is identical on both platforms:

- Compose Multiplatform product presentation and the shared navigation state built with Navigation 3;
- AndroidX ViewModel with UDF/MVVM, StateFlow and Flow for durable presentation state and one-shot effects;
- public Platform models, serialization/validation, and Ktor Client adapters;
- capture queue models, state transitions, idempotency, retry classification, and repository contracts;
- Room KMP repositories and DataStore KMP settings only where their semantics are genuinely identical;
- common time, logging, capability, and operation-projection rules;
- common tests and synthetic fixtures.

KMP exposes narrow interfaces when it needs an operating-system action. Those interfaces carry native errors and lifecycle outcomes rather than converting them to success or generic absence.

### Native adapter ownership

The Android and iOS shells own behavior governed by the operating system:

- Android lifecycle and iOS lifecycle, scenes, restoration, and system presentation;
- Android `ACTION_SEND`/`ACTION_SEND_MULTIPLE` and the iOS Share Extension/`NSItemProvider` lifecycle;
- Android content URI grants, iOS security-scoped resources, staging and other file access;
- Android Keystore and iOS Keychain storage and user-presence policy;
- WorkManager and background URLSession scheduling, cancellation, and expiration;
- permissions, entitlements, notifications, deep links, and platform accessibility integration;
- app/extension coordination, app-group access, and OS-specific diagnostics.

Share surfaces remain native even though the main apps host shared Compose content. An extension may reuse pure shared models and queue rules; it does not load the full application graph merely for symmetry.

### Apple interop

The initial iOS shell imports a static Objective-C framework generated by Kotlin/Native and hosts its Compose `UIViewController`. This is the mature interop path for the first scaffold. Swift Export is considered selectively only when a concrete non-UI API becomes materially clearer in Swift and its compatibility constraints are tested; it is not enabled globally.

## Rationale

One shared Compose presentation keeps routes, visible state, partial/error handling, and accessibility semantics aligned. Thin native shells preserve the platform authority boundary: a transient URI grant, an expiring extension request, a background task deadline, and a secure-storage denial are not portable implementation details.

The seam is therefore based on behavioral sameness, not source-file symmetry. Platform adapters can evolve independently while shared code remains a deep module around product state and queue/API rules.

## Consequences

### Positive

- Android and iOS use one presentation and UDF state model.
- Queue and Platform contract behavior can be tested once across both targets.
- Native lifecycle, share, file, background, and security failures remain explicit.
- ObjC interop keeps the first iOS build predictable while leaving selective Swift Export available later.

### Costs

- The iOS app carries the Compose/Kotlin framework and its build cost.
- Native adapters and shared interfaces require deliberate error and cancellation mapping.
- A shared UI regression can affect both platforms, so both platform builds and shared tests are mandatory in CI.

## Android/iOS lifecycle impact

The shared Compose root survives only through state supplied by shared repositories and native lifecycle adapters. It does not assume an Activity, scene, Share Extension, or background worker remains alive. Android and iOS entry points persist or stage work before their transient lifecycle completes in later plan items.

## Security and privacy impact

Provider credentials never enter KMP or the mobile client. Device secrets remain in Keystore/Keychain. Shared code receives the least information needed through typed adapters; URI/bookmark handles, notification contents, and diagnostics keep the repository's minimization and redaction rules.

## Compatibility and schema impact

This decision creates no wire-format or database change. Ratatoskr keeps one public API version and one current schema definition. The shared models consume the pinned Platform OpenAPI document; changing that pin is an explicit generated-contract update, not version negotiation.

## Validation

- `tooling/tests/architecture_boundary_test.sh` checks that every required responsibility and the Apple interop decision are recorded.
- Android compilation proves the native Activity hosts the shared Compose root.
- Kotlin/Native framework linking and unsigned Xcode simulator build prove the SwiftUI/UIKit shell hosts that same root.
- Shared tests run on Android host and iOS Simulator targets.

## Follow-up

Later plan items may split the single shared module when executable queue, API, or persistence seams justify deeper modules. They must preserve this ownership decision or replace it with a new accepted ADR.
